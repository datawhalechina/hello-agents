# 基于 Hello-Agents 第十四章的找实习助手 Agent 方案

## 1. 第十四章内容总结

Hello-Agents 第十四章主题是“自动化深度研究智能体”，目标是构建一个能自动搜索、分析资料并生成研究报告的 DeepResearch 类应用。它面向知识密集型任务，重点解决三个问题：

- 问题剖析：把开放式研究主题拆成可搜索、可执行的子任务。
- 多轮信息采集：调用搜索工具持续获取资料，去重、整理并保留来源。
- 反思与总结：基于阶段性结果判断信息是否充分，最后生成结构化报告。

系统采用前后端分离架构：

- 前端层：Vue 3 + TypeScript，负责输入研究主题、展示实时进度和 Markdown 报告。
- 后端层：FastAPI，提供 `/research/stream` 这类流式接口。
- 智能体层：HelloAgents，包含 TODO Planner、Task Summarizer、Report Writer 三个 Agent。
- 工具层：SearchTool、NoteTool，以及搜索引擎、LLM 等外部服务。

整体工作流是：

1. 用户输入研究主题。
2. Planner Agent 将主题拆成 3-5 个 TODO 子任务。
3. SearchService 为每个子任务执行搜索。
4. Summarizer Agent 对搜索结果做结构化总结，并保留引用来源。
5. NoteTool 把每个子任务的搜索结果和总结保存成 Markdown 笔记。
6. Report Writer Agent 汇总所有子任务结果，生成最终研究报告。
7. FastAPI 通过 SSE 把进度、日志、任务状态和最终报告实时推送给前端。

第十四章的核心范式是 TODO 驱动研究，也就是“规划 -> 执行 -> 整合”。这个范式比一次性问答更稳定，因为每个阶段都有明确输入输出，方便调试，也方便替换搜索源、提示词或报告格式。

## 2. 用到的关键知识点

### 2.1 多 Agent 顺序协作

第十四章没有让一个 Agent 包办所有事情，而是拆成三个专家 Agent：

- TODO Planner：负责拆解研究问题，输出 JSON 格式任务列表。
- Task Summarizer：负责阅读搜索结果，提炼核心观点、关键数据和来源引用。
- Report Writer：负责合并多个任务总结，生成结构化 Markdown 报告。

这种设计的好处是职责清晰、Prompt 更容易优化、单个模块出错时更容易定位。

### 2.2 TODO 驱动任务分解

复杂任务不是直接执行，而是先规划成 3-5 个子任务。每个子任务包含：

- title：任务标题。
- intent：为什么要研究这个子问题。
- query：用于搜索引擎的查询语句。

这让研究过程从“模糊探索”变成“可检查的执行清单”。

### 2.3 工具调用与 ToolRegistry

SearchTool、NoteTool 都通过工具注册表管理。Agent 可以调用工具，工具返回结构化结果。这个模式适合继续扩展新的能力，例如招聘网站搜索、简历解析、岗位匹配评分、邮件生成等。

### 2.4 ToolAwareSimpleAgent

第十四章扩展了 SimpleAgent，加入工具调用监听能力。每次工具调用时都可以记录：

- 哪个 Agent 调用了工具。
- 调用了什么工具。
- 参数是什么。
- 返回结果是什么。

这对调试、日志记录、前端进度展示都很重要。

### 2.5 搜索调度与信息处理

SearchService 不只是调用搜索 API，还负责：

- 按配置选择 Tavily、DuckDuckGo、Perplexity、SearXNG 等搜索源。
- 去重 URL。
- 限制每个来源的 token 长度。
- 处理搜索失败。
- 可选地加入搜索缓存，减少成本和重复请求。

### 2.6 结构化输出解析

Planner Agent 输出 JSON，后端要做解析和字段验证。第十四章用正则提取 JSON 数组，再用 `json.loads` 解析，并检查 `title`、`intent`、`query` 是否齐全。

### 2.7 持久化笔记

NoteTool 会把每个子任务的搜索结果、总结和最终报告保存到工作区。这样可以复盘研究过程，也可以在中断后恢复或复用历史资料。

### 2.8 SSE 实时进度

后端用 FastAPI `StreamingResponse` 返回 `text/event-stream`，前端用 EventSource 接收事件。它适合长时间任务，因为用户可以看到“正在规划、正在搜索、正在总结、正在生成报告”等状态，而不是一直等待。

### 2.9 Markdown 报告渲染

最终结果用 Markdown 组织，前端用 marked 等库渲染。这样既适合阅读，也方便保存、复制、二次编辑。

## 3. 将其改造成找实习助手 Agent 的可行性分析

你的想法可行，而且和第十四章的架构匹配度很高。

深度研究 Agent 本质上是在做“信息发现 -> 信息整理 -> 结构化决策辅助”。找实习也正是这类任务：岗位信息分散、更新快、需要比较和筛选、还要结合个人简历判断匹配度。

可以把第十四章的三个 Agent 映射成找实习场景：

- TODO Planner -> 求职计划规划 Agent  
  输入用户目标，例如“找 2026 暑期后端开发实习，地点杭州/上海，偏 Java 和 AI 应用”。输出若干任务：搜索岗位、分析目标公司、提取 JD 要求、匹配技能差距、生成投递建议。

- Task Summarizer -> 岗位分析 Agent  
  对每批搜索结果或岗位 JD 做总结，提取公司、岗位、地点、技术栈、学历要求、实习周期、投递链接、截止时间、亮点和风险。

- Report Writer -> 求职行动报告 Agent  
  汇总岗位列表，给出优先级、匹配理由、待补技能、简历修改建议和投递计划。

此外，需要新增几个面向求职的能力：

- 简历解析：读取用户简历或自我介绍，抽取技能、项目、教育背景、意向城市和时间安排。
- 岗位结构化抽取：从网页或 JD 文本中抽取统一字段。
- 匹配评分：根据技能、城市、时间、学历、项目经历等维度打分。
- 去重与跟踪：同一公司同一岗位可能出现在多个平台，需要按公司、岗位名、地点、链接去重。
- 投递状态管理：记录“待投递、已投递、笔试、面试、拒绝、offer”等状态。
- 简历/邮件生成：基于岗位要求生成定制化简历修改建议、求职邮件或内推私信草稿。

## 4. 推荐的 MVP 范围

第一版不要一上来做全自动投递，建议先做“找岗位 + 分析岗位 + 给行动建议”的半自动助手。

MVP 输入：

- 目标岗位：如后端开发、算法、AI 产品、数据分析。
- 城市偏好：如上海、杭州、北京、远程。
- 用户背景：简历文本或简短自我介绍。
- 约束条件：实习时长、到岗时间、技术偏好、公司类型偏好。

MVP 输出：

- 10-20 个候选实习岗位。
- 每个岗位的结构化信息：公司、岗位、地点、要求、链接、发布时间或截止时间。
- 匹配评分和理由。
- 高优先级投递清单。
- 针对前 3-5 个岗位的简历修改建议。
- 一份 Markdown 格式的找实习行动报告。

## 5. 建议的 Agent 架构

### 5.1 Internship Planner

职责：根据用户目标和简历，规划本轮找实习任务。

输出示例：

```json
[
  {
    "title": "搜索后端开发实习岗位",
    "intent": "找到符合城市和技术栈偏好的岗位",
    "query": "2026 暑期实习 后端开发 Java 上海 杭州 招聘"
  },
  {
    "title": "搜索 AI 应用开发实习岗位",
    "intent": "寻找与 Agent/LLM 项目经历相关的岗位",
    "query": "AI Agent 实习 LLM 应用开发 实习生 招聘"
  }
]
```

### 5.2 Job Search Service

职责：执行搜索和结果清洗。可以先复用 SearchTool，后续再接入专门招聘平台。

第一版可搜索：

- 公司官网招聘页。
- 牛客、实习僧、Boss 直聘、猎聘、拉勾等公开页面。
- GitHub、公众号、学校就业网、企业校招官网。

注意：部分招聘平台有反爬和登录限制，第一版建议以搜索引擎结果和用户粘贴 JD 为主，不要强依赖爬虫。

### 5.3 JD Extractor

职责：把岗位页面或 JD 文本转为统一结构。

字段建议：

- company
- title
- location
- department
- requirements
- responsibilities
- tech_stack
- education
- duration
- start_date
- deadline
- source_url
- posted_at

### 5.4 Match Scorer

职责：根据用户画像和岗位要求计算匹配度。

评分维度：

- 技术栈匹配：如 Python、Java、Vue、FastAPI、LLM、RAG。
- 项目经历匹配：是否有相关项目可写进简历。
- 城市与到岗时间匹配。
- 学历和年级要求匹配。
- 岗位成长价值：是否适合当前目标。
- 投递难度：大厂、热门岗位、是否要求强算法等。

### 5.5 Application Advisor

职责：输出投递建议。

输出内容：

- 投递优先级。
- 简历应该突出哪些项目。
- 需要补的技能关键词。
- 针对岗位的求职邮件或内推私信草稿。
- 后续跟进计划。

### 5.6 Report Writer

职责：生成最终 Markdown 报告，包括岗位清单、匹配分析、投递计划和风险提示。

## 6. 技术实现路线

### 阶段 1：命令行 MVP

目标：先跑通核心逻辑，不做复杂前端。

任务：

- 创建 `internship_agent` 项目结构。
- 实现用户画像输入：手动填写或粘贴简历。
- 复用 SearchTool 搜索岗位。
- 实现 JD 结构化抽取 Prompt。
- 实现匹配评分 Prompt。
- 输出 `reports/internship_report.md`。

### 阶段 2：加入持久化与状态管理

目标：让找实习过程可持续跟踪。

任务：

- 用 NoteTool 或本地 JSON/SQLite 保存岗位。
- 增加投递状态字段。
- 支持去重。
- 支持重新评分和更新岗位状态。

### 阶段 3：Web 前端

目标：复用第十四章的 Vue + FastAPI + SSE 体验。

任务：

- 输入求职目标和简历。
- 展示搜索进度。
- 展示岗位表格、匹配分、投递状态。
- 支持导出 Markdown 报告。

### 阶段 4：增强自动化

目标：从“分析助手”升级为“投递工作台”。

任务：

- 接入更多岗位来源。
- 增加定时搜索和岗位更新提醒。
- 根据岗位生成定制化简历要点。
- 生成面试准备清单。
- 支持按岗位生成项目经历改写建议。

## 7. 风险与限制

- 招聘信息更新快：必须保留来源链接和抓取时间，避免使用过期岗位。
- 平台访问限制：很多招聘平台需要登录或反爬，不能假设所有页面都能稳定抓取。
- JD 信息不完整：有些岗位没有截止时间、部门或明确技术栈，需要标记“不确定”。
- 自动投递风险高：自动点击投递可能误投或违反平台规则，建议先做人类确认的半自动流程。
- 匹配评分有主观性：评分应给出理由，不能只给数字。
- 隐私问题：简历包含手机号、邮箱、学校、经历，必须避免上传到不可信服务，日志中也要注意脱敏。

## 8. 结论

基于第十四章开发找实习助手 Agent 是一个很好的方向。它不是简单换个 Prompt，而是把 DeepResearch 的“任务分解、搜索、总结、引用、报告、实时进度”迁移到求职场景。

最推荐的第一版是半自动找实习助手：

- 用户提供目标和简历。
- Agent 搜索并整理岗位。
- Agent 抽取 JD 并评分。
- Agent 输出投递优先级和简历修改建议。
- 用户自己确认并投递。

这样既能体现 Agent 的价值，又能避开自动投递、登录爬虫、隐私泄露等高风险问题。等 MVP 稳定后，再逐步加入岗位数据库、状态追踪、定时更新和前端工作台。
