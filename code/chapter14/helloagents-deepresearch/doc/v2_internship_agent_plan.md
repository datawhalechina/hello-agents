# 第二版找实习助手产品计划

更新时间：2026-06-11

## 1. 产品定位

第二版找实习助手不应只是“搜索岗位并生成报告”的 Research Agent，而应升级为“帮学生决定今天投哪些、怎么改简历、如何持续推进”的 Internship Action Agent。

当前产品已经具备真实 SSE 流程、岗位推荐清单、搜索质量诊断、最终 Markdown 报告、本地岗位保存和投递状态管理。v2 的重点应从“能跑通”转向“让用户更快做出下一步动作”。

一句话定位：

```text
输入求职画像，输出可信岗位清单、投递优先级、简历优化建议和可跟踪行动计划。
```

## 2. 当前核心问题与目标用户

### 2.1 当前解决的问题

当前版本主要解决学生找实习早期的三个问题：

- 信息分散：岗位、JD、投递渠道分布在招聘平台、企业官网、校招站、公众号和讨论区。
- 难以判断：学生不知道岗位是否适合自己，也不容易从 JD 中提炼关键要求。
- 行动模糊：搜索完以后，不知道今天该投哪些、简历该改哪里、接下来一周如何安排。

当前系统已经能将一句自然语言求职目标转换为：

- 求职任务规划。
- 岗位/JD/渠道搜索。
- 结构化岗位清单。
- 搜索质量诊断。
- 找实习行动报告。
- 本地岗位保存与投递状态跟踪。

### 2.2 目标用户

优先目标用户：

- 正在找暑期实习、日常实习或校招前置实习的本科生、研究生。
- 技术岗候选人，例如后端、前端、AI 应用、数据分析、算法工程等方向。
- 有一些项目经历，但缺少岗位判断、简历包装和投递节奏经验的学生。

次级目标用户：

- 正在准备转方向实习的学生。
- 想快速了解某类岗位市场要求的学生。
- 想把投递过程做成清单管理的学生。

## 3. 当前版本体验短板

### 3.1 输入不够结构化

当前主要依赖自然语言 `topic` 输入。优点是灵活，缺点是用户不知道该写哪些关键信息，搜索质量和匹配质量容易受输入完整度影响。

典型缺失信息包括：

- 目标方向。
- 城市偏好。
- 到岗时间。
- 实习周期。
- 技术栈。
- 项目亮点。
- 公司类型偏好。
- 是否接受远程。

产品价值：高。  
实现复杂度：低到中。  
风险：低。

### 3.2 等待过程的价值感不够稳定

真实 SSE 流程可能持续 1-4 分钟，虽然已有进度展示，但用户仍可能不清楚：

- 当前搜到的岗位是否可靠。
- 为什么有些结果被过滤。
- 当前是否已经有可用结果。
- LLM 限流或 fallback 时结果可信度如何。

产品价值：中到高。  
实现复杂度：中。  
风险：低。

### 3.3 岗位清单还不够“决策化”

当前岗位清单已经有匹配分、来源、JD 要求、简历建议和风险，但还缺少用户高频需要的操作：

- 按匹配度排序。
- 按城市、来源、状态筛选。
- 对比 2-3 个岗位。
- 标记“待确认”“优先投递”“暂不投”。
- 将搜索结果转化为今日投递计划。

产品价值：高。  
实现复杂度：中。  
风险：中，评分和排序必须有可解释原因。

### 3.4 报告偏汇总，行动牵引还可以更强

当前最终报告已经能兜底生成，但 v2 应把报告从“搜索结果总结”升级成“投递作战单”。

报告顶部应该先回答：

- 今天最值得投哪 3-5 个岗位？
- 为什么先投它们？
- 简历最该改哪 3 点？
- 接下来 7 天怎么推进？
- 哪些信息必须点开来源确认？

产品价值：高。  
实现复杂度：低。  
风险：低。

### 3.5 投递跟踪还是简单状态记录

当前支持保存岗位、更新状态、备注、删除岗位。v2 应进一步支持轻量投递管理：

- 投递渠道。
- 投递日期。
- 下一步动作。
- 简历版本。
- 待跟进时间。
- 放弃原因。

产品价值：高。  
实现复杂度：中。  
风险：低。

### 3.6 简历优化不够贴身

当前简历建议主要来自岗位/JD 分析，后续应允许用户粘贴“非敏感的项目经历/技能摘要”，让建议更贴近用户真实背景。

需要注意：

- 不默认上传或长期保存完整简历。
- 不编造经历。
- 不建议伪造技能。
- 明确区分“可直接改写”和“需要用户补充事实”。

产品价值：高。  
实现复杂度：中。  
风险：中，涉及隐私和真实性边界。

## 4. v2 优先解决的问题

### 4.1 结构化求职画像

目标：降低用户输入门槛，提高搜索和匹配质量。

建议字段：

- 目标岗位方向。
- 城市偏好。
- 到岗时间。
- 实习周期。
- 技术栈。
- 项目亮点。
- 学历/年级。
- 公司类型偏好。
- 是否接受远程。
- 其他限制。

落地方式：

- v2.0 不必修改后端协议。
- 前端用结构化表单收集信息。
- 提交前拼接成现有 `/research` 和 `/research/stream` 所需的 `topic`。
- 后续再考虑新增兼容字段，例如 `profile`，但不能破坏旧 API。

### 4.2 岗位可信度与优先级决策

目标：让用户知道“哪些岗位值得点开和优先投递”。

建议新增或强化展示：

- 来源类型：企业官网、校招官网、招聘平台、学校就业网、公众号、未知。
- 来源可信度：高/中/低。
- 信息完整度：有公司、职位、地点、JD、投递入口、截止日期等。
- 推荐优先级：优先投递、可以投递、待确认、暂缓。
- 待确认项：是否仍开放、城市是否匹配、是否要求学历/年级、是否需要现场实习。

实现方式：

- 复用现有 `job_items` 和 `search_diagnostics`。
- 可以先在前端计算部分展示标签。
- 后端后续可扩展字段，但保持旧字段兼容。

### 4.3 行动报告升级

目标：让报告直接指导用户接下来做什么。

建议报告结构：

```text
# 找实习行动报告

## 1. 结论：今天优先投递
列出 3-5 个最推荐岗位。

## 2. 推荐理由
解释岗位与用户画像的匹配点。

## 3. 简历修改清单
给出可执行修改建议。

## 4. 7 天投递计划
拆成今天、3 天内、7 天内。

## 5. 风险与待确认项
列出信息不完整、可能过期、要求不明确的地方。

## 6. 附录：来源与搜索诊断
保留来源链接和搜索质量说明。
```

### 4.4 投递跟踪升级为轻量看板

目标：让产品从一次性搜索工具变成持续使用工具。

建议状态仍保持当前集合：

```text
待投递、已投递、笔试、面试、拒绝、Offer、放弃
```

建议新增字段：

- application_channel：投递渠道。
- applied_at：投递日期。
- next_action：下一步动作。
- next_action_at：下一步提醒时间。
- resume_version：使用的简历版本。
- reject_reason：放弃或拒绝原因。

落地方式：

- 基于现有 `/applications` 扩展。
- 新字段必须可选，保证旧数据可读。
- v2.0 可先做列表分组，v2.1 再做看板视图。

### 4.5 简历定向优化

目标：基于岗位和用户真实背景给出更贴近投递的建议。

v2.0 推荐做法：

- 前端增加“项目经历/技能摘要”输入区。
- 明确提示不要粘贴身份证、手机号、邮箱、完整住址等敏感信息。
- 默认不长期保存该文本。
- 报告中输出“针对高优先级岗位的简历修改建议”。

输出要求：

- 每条建议对应一个岗位或一类岗位。
- 标注建议依据。
- 不编造经历。
- 对缺失事实使用“建议补充说明”，而不是直接生成虚假内容。

## 5. 高价值低风险功能

优先推进：

- 结构化求职画像表单。
- 岗位排序和筛选。
- 可信来源标签。
- 岗位待确认项。
- 今日投递清单。
- 7 天行动计划。
- 手动保存岗位。
- 投递渠道和下一步动作记录。
- 简历摘要输入与定向建议。
- 报告复制和导出优化。
- 空结果时的搜索建议。

这些功能有三个共同点：

- 与真实用户价值直接相关。
- 可以复用现有 API、SSE 和数据结构。
- 不涉及自动投递、平台登录或绕过限制。

## 6. 应暂缓功能

暂不做：

- 自动投递。
- 批量投递。
- 自动联系 HR。
- 自动私信、批量骚扰、批量邮件。
- 登录招聘平台抓取。
- 绕过招聘平台访问限制。
- 大规模爬虫和实时岗位库。
- 多用户账号系统。
- 云端同步。
- 长期保存完整简历。
- 一键生成“完美简历”。
- 复杂多 Agent 自治投递流程。

原因：

- 法务、平台规则和用户安全风险高。
- 容易偏离“辅助决策”的产品边界。
- 对当前项目的工程复杂度提升很大，但不一定提升 v2 的核心用户价值。

## 7. v2 用户主流程

建议主流程：

```text
填写求职画像
-> 启动找实习流程
-> 实时查看搜索进度和质量诊断
-> 获取岗位清单
-> 筛选、排序、查看岗位详情
-> 保存优先岗位
-> 生成行动报告
-> 根据报告修改简历和人工投递
-> 在本地清单中跟踪投递状态
```

关键体验原则：

- 第一屏让用户明确输入什么。
- 搜索中持续给用户“已经产出了什么”。
- 岗位清单优先展示可行动信息。
- 报告先给结论，再给解释。
- 投递跟踪必须轻，不要做成复杂 CRM。

## 8. 模块升级建议

### 8.1 岗位搜索

升级目标：

- 提升可靠岗位比例。
- 降低空结果和噪声结果。
- 解释搜索质量。

建议：

- 使用结构化画像生成搜索 query。
- 保留招聘详情页优先策略。
- 保留平台定向 query。
- 针对不同岗位方向生成不同关键词模板。
- 空结果时输出可执行建议，例如扩大城市、换关键词、切换搜索后端。
- 搜索结果必须保留来源链接和来源标题。

### 8.2 岗位筛选

升级目标：

- 帮用户快速决定投递顺序。

建议筛选项：

- 城市。
- 远程/现场。
- 匹配分。
- 来源可信度。
- 是否已保存。
- 是否有明确投递入口。
- 是否有待确认风险。

建议排序：

- 推荐优先。
- 匹配分最高。
- 风险最低。
- 来源最可信。
- 最近保存。

### 8.3 报告生成

升级目标：

- 从总结型报告转为行动型报告。

建议：

- 报告顶部放“今天优先投递”。
- 每个推荐岗位给出推荐理由和待确认项。
- 简历建议按岗位聚合。
- 明确写出 24 小时、3 天、7 天计划。
- fallback 报告也要保持该结构。

### 8.4 投递跟踪

升级目标：

- 从状态记录变成轻量行动管理。

建议：

- 增加投递渠道。
- 增加投递日期。
- 增加下一步动作。
- 增加简历版本备注。
- 支持按状态分组展示。
- 支持手动添加岗位。

### 8.5 简历优化

升级目标：

- 针对具体岗位给出真实、可改、可验证的建议。

建议：

- 支持用户粘贴项目经历/技能摘要。
- 给出“应该强化的项目点”。
- 给出“JD 关键词覆盖建议”。
- 给出“需要补充事实”的提醒。
- 不生成虚假经历。
- 不默认持久化敏感文本。

## 9. 成功指标

建议使用以下可验证指标衡量 v2 是否成功：

| 指标 | 目标 |
| --- | --- |
| SSE 完成率 | `/research/stream` 收到 `done` 的比例不低于 85% |
| 可用岗位产出率 | 每次搜索至少产出 3 个可靠岗位的比例不低于 70% |
| 可靠来源比例 | 可靠岗位数 / 原始搜索结果数不低于 30% |
| 首个岗位出现时间 | P75 小于 60 秒 |
| 完整报告生成时间 | P75 小于 180 秒 |
| 岗位保存率 | 生成岗位后用户保存至少 1 个岗位的会话比例不低于 50% |
| 投递状态推进率 | 保存岗位后状态推进到“已投递”的比例不低于 30% |
| 报告结构完整率 | 报告包含推荐岗位、简历建议、行动计划、风险提示的比例不低于 95% |
| fallback 可用率 | LLM 限流或失败时仍返回可读报告的比例不低于 95% |

## 10. 分阶段路线图

### 10.1 v2.0 必做

- 结构化求职画像表单。
- 表单内容兼容拼接为现有 `topic`。
- 岗位清单排序和筛选。
- 可信来源、风险、待确认项展示。

### 10.2 v2.1 可做

- 手动添加岗位到跟踪列表。
- 岗位对比视图。

## 11. 简洁 PRD

### 11.1 产品目标

帮助正在找实习的学生从模糊求职目标出发，得到可信岗位清单、投递优先级、简历优化建议和可跟踪行动计划。

v2 的核心目标不是堆更多 Agent 技术，而是提升真实找实习过程中的决策效率和行动转化。

### 11.2 用户故事

- 作为找实习的学生，我希望输入自己的方向、城市、技能和时间，系统能帮我找到值得投的岗位。
- 作为缺少投递经验的学生，我希望知道每个岗位为什么适合我、哪里不匹配。
- 作为正在投递的学生，我希望保存岗位并跟踪投递状态。
- 作为准备改简历的学生，我希望根据具体 JD 得到不编造经历的修改建议。
- 作为需要复盘的学生，我希望看到自己还有哪些岗位待投递、哪些岗位需要跟进。

### 11.3 功能清单

v2.0 功能：

- 求职画像表单。
- SSE 实时搜索进度。
- 岗位推荐清单。
- 岗位排序和筛选。
- 搜索质量诊断。
- 岗位详情与来源核验提示。
- 保存岗位与投递状态管理。
- 投递渠道、投递日期、下一步动作、简历版本备注。
- 行动报告生成。
- 简历定向优化建议。
- 复制和导出结果。

### 11.4 非功能要求

- 不破坏现有 API 和 SSE 协议。
- 新增字段采用兼容式扩展。
- 不提交 `.env`、密钥、运行数据、依赖目录或构建产物。
- 招聘信息必须保留来源链接。
- 限流时必须有 retry 或 fallback。
- 不生成伪岗位。
- 不编造用户经历。
- 不默认长期保存敏感简历文本。
- 前端端口继续固定为 5174。
- 本地保存优先，适合单机开发和演示。

### 11.5 验收标准

输入典型求职目标后，系统应满足：

- SSE 能完成并收到 `done`。
- 页面展示任务进度、岗位清单、搜索质量诊断和最终报告。
- 岗位清单可排序、可筛选、可保存。
- 保存岗位后可修改投递状态和备注。
- 报告包含推荐岗位、投递顺序、简历修改建议、风险与待确认项、7 天计划。
- 空结果时展示原因和下一步搜索建议。
- 429 或 LLM 失败时仍能返回快速版行动报告。
- 不自动投递、不登录平台、不绕过平台限制。

### 11.6 风险与边界

招聘信息变化快：

- 产品只做公开信息整理和决策辅助。
- 必须提示用户点开来源确认。

匹配分具有主观性：

- 必须展示评分理由。
- 不应暗示录用概率。

简历信息涉及隐私：

- 默认不长期保存完整简历。
- 建议用户只粘贴项目经历和技能摘要。
- 不要求身份证、手机号、邮箱、完整住址等敏感信息。

平台规则风险：

- 不做自动投递。
- 不登录招聘平台。
- 不绕过平台访问限制。
- 不批量联系 HR。

内容真实性风险：

- 不编造项目经历。
- 不建议伪造技能。
- 对缺失事实只提示“需要补充”，不替用户虚构。

## 12. 推荐实施顺序

建议按以下顺序推进：

1. 结构化求职画像表单。
2. 岗位排序、筛选和可信度展示。
3. 行动报告结构升级。
4. 投递跟踪字段扩展。
5. 简历摘要输入与定向建议。
6. 手动添加岗位和岗位对比。
7. 本地存储从 JSON 升级到 SQLite。

这样可以最大程度复用当前系统，同时把 v2 的产品价值集中在真实用户最需要的“找得到、看得懂、投得动、跟得住”上。
