# FrameCraft 毕业设计答辩材料

## 一分钟介绍

FrameCraft 是一个从 Figma Frame 到 React 页面骨架的多智能体应用。它解决的具体问题是，开发者拿到设计之后，要重复读取布局、整理组件、写样式并核对遗漏，而且很难追溯某段生成代码来自哪个设计节点。

我的方案保留设计节点 ID，把结构理解、组件规划、生成计划和评审交给四个 HelloAgents `SimpleAgent`；再由确定性编译器生成 React、TypeScript、CSS 和静态预览。开发者可以同时查看生成页面、执行过程、组件计划和质量报告。

这个原型的目标是减少单页基础结构的重复工作。复杂图片、矢量、业务交互和视觉一致性仍有明确限制，所以系统会显示占位与警告，不把结构覆盖率当成视觉还原率。

## 五分钟演示顺序

1. **说明场景，约 30 秒。** 展示输入示例和目标页面类型，说明输入是设计结构，不是已经写好的网页。
2. **运行离线流程，约 1 分钟。** 启动 `python main.py serve`，选择内置示例与 demo。展示实际阶段状态、预览和文件，并明确这一步没有调用模型。
3. **解释四角色协作，约 1 分钟。** 展示 DesignAnalyst、ComponentPlanner、CodeEngineer、Reviewer 各自的输入输出契约。若已配置模型，运行 live 并展示真实轨迹；若没有，直接说明在线部分未实测。
4. **检查证据，约 1 分钟。** 打开 `component-plan.json`、`design-model.json` 和 `review-report.json`，根据一个 node ID 对照源码。说明警告如何暴露不支持的设计内容。
5. **说明结果与限制，约 1 分钟。** 用 `docs/evaluation.json` 报告已实际执行的测试、构建或服务联调。展示 ZIP 导出，说明后续工程接入与人工复核成本。
6. **保留约 30 秒。** 回答为什么选择受限生成，以及下一步最值得投入的能力。

演示前先做一次离线运行，并为每次 CLI 演示使用新的输出目录，避免已有目录造成写入失败。在线演示依赖网络、额度与服务状态，应备好已有运行的真实证据；演示回放必须标明回放，不能把离线结果当成实时模型输出。

## 可以直接解释的设计选择

### 为什么使用多 Agent

四个角色把设计事实、组件语义、生成契约和评审意见拆开，便于分别约束与检查。前序输出作为后序的数据输入，每一步均有可验证格式。代价是四次模型调用带来的延迟和费用，而且多角色并不天然保证比单角色更准确。要证明质量提升，需要同一批设计上的单 Agent 对照实验；本项目没有这类实验时，不宣称已经证明提升。

### 为什么模型不直接写全部代码

布局、尺寸和颜色大部分已经存在于 Figma 数据中，让模型重新猜这些数值会引入不必要的漂移。确定性编译器保留设计事实，模型只补充有限的结构语义。代价是输出能力受编译器支持范围约束，扩展复杂效果要写明确的转换规则。

### 这算不算 Agent

live 模式确实实例化并调用了四个 HelloAgents `SimpleAgent`，各有角色目标、上下文和结构化结果；整体采用固定工作流编排。它不是能自主使用浏览器和终端的通用编码 Agent。demo 没有模型调用，应称为离线演示。答辩应准确说明这种自主性边界。

### Reviewer 的修复能力到哪里

Reviewer 可返回一次合法的替代组件计划，系统对它重新校验、编译和检查。它不能修改原设计事实、凭空补全业务规格或无限调用模型。修复只针对当前受控计划范围，不等同于截图驱动的视觉回归修复。

### 为什么按钮不能点击

仅有按钮外观无法确定业务含义和接口契约。项目默认输出禁用按钮，提醒开发者补充交互规格。要实现完整功能，还需要流程、数据、错误状态、可访问性和测试要求。

### 失败如何处理

输入超限、无效节点、Figma 权限或限流错误、模型返回无效 JSON 等都有明确失败路径。在线失败不会自动变成 demo 成功。后续可以增加重试和恢复，但必须计入请求次数、成本与状态，避免重复扣费和模糊结果来源。

## 评价口径

| 维度 | 推荐记录 | 报告边界 |
| --- | --- | --- |
| 可运行性 | 环境、命令、退出码、耗时 | 必须有实际执行记录 |
| 结构完整度 | 导入节点数、覆盖情况、缺失警告 | 不是视觉准确率 |
| 输出工程 | 生成文件、TypeScript / Vite 构建结果 | 静态预览不能替代构建 |
| 异常处理 | 超限、无效 JSON、错误 URL、缺少配置 | 桩测试不等于远程服务联调 |
| 多 Agent | 模式、各角色调用状态、耗时、修复次数 | demo 不计真实模型调用 |
| 视觉质量 | 未来增加同尺寸截图与人工问题清单 | 当前无基准时保持未评价 |
| 成本 | 服务实际 usage 与价格、运行时长 | 字符上限不能转换成固定费用 |

离线评估见 [evaluation.json](evaluation.json)，测试、实际构建、浏览器与在线接入状态见 [validation.json](validation.json)。不要填写估算出来的“准确率”“节省工时”或“全平台支持”。

## 开发中实际遇到的问题

| 问题 | 修正与证据 |
| --- | --- |
| 窄屏统计文字被挤碎，进度条消失 | 通用换行规则覆盖了小图形的固定高度；缩小规则作用范围，为伸缩列设置最小宽度，重新构建并检查 390px 页面 |
| 按钮里的大字号文案被当成页面标题 | 名称与字号启发式需要考虑祖先；按钮子树不再分配标题与导航语义，增加回归测试 |
| 在线分析返回错误的 JSON 契约 | 公共提示混入了其他角色的计划约束；拆分角色提示，保留严格 schema，明确报告格式错误，重新进行真实调用验证 |

这些问题说明 D2C 不能只看一次演示截图。输入边界、布局规则、模型提示与真实运行都需要独立检查。在线修正后的最终结果以验证记录为准。

## 毕业设计贡献与后续工作

本项目的主要工程贡献是建立一条有来源、有限额、有产物契约的 D2C 流程；同时把 demo 与 live、结构与视觉、生成与构建的证据分开，让评审能够判断系统真正完成了什么。

下一步优先接入图片和矢量资产，再建立真实 Figma 样本及截图基准。之后才评估是否引入设计系统组件库、跨页路由和更多自动修复。每一步都应增加对应验收证据，避免功能列表增长而可用性没有提升。

本项目按照 [Hello-Agents 第 16 章](https://github.com/datawhalechina/hello-agents/blob/main/docs/chapter16/%E7%AC%AC%E5%8D%81%E5%85%AD%E7%AB%A0%20%E6%AF%95%E4%B8%9A%E8%AE%BE%E8%AE%A1.md) 的可运行项目、依赖、README 与共创目录要求准备。是否提交 PR、是否被社区合并，应以真实记录为准。
