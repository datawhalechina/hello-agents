# 垂直场景 Agent 的自建评测：从 baseline 阶梯到预注册判据

第十二章讲了怎么用 BFCL、GAIA 这类公开基准评估智能体，也讲了怎么用 LLM Judge 和 Win Rate 评估生成质量。但做完第十六章的毕业设计之后，你大概率会撞上另一个问题：

> 我做的是一个垂直场景的 Agent。没有现成的基准能测它。我怎么证明它真的比一次普通的 RAG 好？

这个问题第十二章的习题其实问了三遍——习题 1 让你为智能客服设计评估指标，习题 3 让你自建一套领域评估集，习题 5 让你设计分层评估策略——但正文没有给方法。这一章就是补这一段。

内容来自我做的一个**代码库 onboarding 问答系统**，用户提交一个 Python 仓库，系统做结构化索引，然后回答"这个功能在哪实现的""这条调用链怎么走"这类问题，每条引用都要能点回具体的文件、符号和行号。三人课程项目，我负责架构和大部分实现。

先把结论摆在前面，因为它是这一章最重要的部分：

> **我们预先注册的主假设，最终判定是 `unsupported`。四项比较通过了三项，差 0.0061。**

这一章是一份评测施工记录：我怎么造题、怎么搭对照、怎么在跑之前锁死判据、怎么发现自己的指标能被反向刷高，以及最后为什么没有把不利结论改掉。

如果你只想带走一件事，那就是这句：**评测要得到的是一个有机会推翻你的结论。**

本章的可执行版本在共创项目 [Odiethebest-CodebaseOnboardingAgent](../Co-creation-projects/Odiethebest-CodebaseOnboardingAgent/)：`main.ipynb` 的 Part 4 就是下面这套流程的最小实现：10 道题，三个进判据的对照臂加三个诊断臂，不需要 API Key，完全确定性可复现。

## 第一章：三个成功截图为什么不算证明

课程项目答辩，最常见的做法是挑三个回答得漂亮的问题截图，配一段"系统能够准确理解代码库语义"。

这只能证明系统偶尔能工作。它回答不了三个更要紧的问题：

1. 它到底比一次普通的向量 RAG 好多少？
2. 如果好，好在哪一块——是混合检索，是 Agent 的多步取证，还是我费了最大力气做的静态调用图？
3. 换一批题、换一天再跑，结论还成立吗？

第三个问题最容易被忽略，也最致命。我们后面会看到，同一套配置跑三轮，单轮结论会翻转。

所以我把评测目标改写成一组**可以被推翻**的问题：随着能力逐级加入，检索质量和最终证据质量是否稳定变好；完整系统在跨文件题和架构题上，是否能以一个**事先说好的幅度**超过它最直接的对手；如果超过了，提升究竟来自哪个模块。

这三句话决定了后面所有的工程：第二句要求你有"直接对手"，也就是 baseline 阶梯；"事先说好的幅度"要求你有预注册判据；第三句要求你有消融臂。

## 第二章：先定义什么叫"一道题"

很多人一开始就卡在这：评测集到底长什么样？

先分清两个东西：

- **测试语料**是被问的对象。我固定了 `psf/requests` 的一个 commit（`414f0513c33883adf6f2b46901d4f0b38a455851`），索引其中 37 个 Python 文件，切出 726 个 chunk（489 个 method、146 个 function、72 个 class、19 个 module docstring），建出 473 条图边。所有对照臂共用同一份索引；运行过程中语料版本一变，这一轮就作废。
- **一道题**是一个可重复执行的评测 case，包含问题、难度层级、构造来源和一组正确证据的锚点。

这是我踩的第一个坑：一开始我以为"标准答案"就是一段写好的文字，然后用 LLM Judge 去比对。后来发现对代码问答来说这条路又贵又不稳——同一个意思有一百种写法，Judge 的分数抖得比系统本身还厉害。

换成**锚点**之后一切都清楚了：

| 字段 | 含义 |
|---|---|
| `id` / `repo_id` | 题目身份与对应语料 |
| `question` | 发给系统的自然语言问题 |
| `taxonomy` | 难度层级：L1 单文件、L2 跨文件、L3 架构级 |
| `gt_targets` | 正确证据的稳定锚点，用 `file_path + symbol_name + start_line` 表示 |
| `gt_files` | 文件级 ground truth，供只能返回文件的对照臂使用 |
| `source` | `manual` 或 `graph_reverse`，保留题目的构造来源 |

举个具体的。这是配套项目 `data/questions.jsonl` 里的一行，原样贴出来：

```json
{"id": "q03", "taxonomy": "L2", "source": "manual",
 "question": "How is basic auth attached to a prepared request?",
 "gt_targets": [{"file": "models.py", "symbol": "prepare_auth",    "start_line": 670},
                {"file": "auth.py",   "symbol": "HTTPBasicAuth",   "start_line": 85},
                {"file": "auth.py",   "symbol": "_basic_auth_str", "start_line": 34}]}
```

它的 gold 是三个源码位置。判分时不需要模型参与，逐条比对锚点就行。

系统最终引用了几个正确目标 → `Recall@5`；第一条正确证据排多靠前 → `MRR`；多个正确证据的整体排序合不合理 → `nDCG@5`。

这样定义有三个好处：**可自动判分**（不需要 Judge）、**可跨版本复用**（锚点比 chunk UUID 稳定，重建索引不会失效）、**边界清楚**（它测的是"有没有找到并引用正确代码"，不测"解释写得好不好"）。

最后一点必须说在明处。我的题集没有人工标准文本答案，所以它**回答不了"解释是否准确、清晰、可执行"**。这是一条范围界定。评测集最怕的就是宣称自己测了没测的东西。

### 题集构成，以及它的偏置

33 道题，全部针对 Requests：

| 层级 | 数量 | 关注点 |
|---|---:|---|
| L1 | 5 | 单文件事实题 |
| L2 | 16 | 跨文件结构关系 |
| L3 | 12 | 架构级端到端链路 |

其中 16 道人工写，17 道用 `graph_reverse` 构造——从系统已经建好的调用关系反推问题，再人工检查。

**这里有个偏置我必须主动说：从系统自己的图反推题目，天然不会包含系统漏建的链路。** 而且这 17 道全落在 L2/L3，题目来源和难度标签是混淆的。它能高效增加图敏感的问题，但不能证明题集无偏。

这类自曝比它看起来更重要。评测报告里主动写出偏置的人，读者才会相信你没写出来的部分。

### 你自己的项目怎么套

把"源码锚点"换成你的领域里**稳定、可自动比对**的坐标：

| 场景 | gold 锚点可以是 |
|---|---|
| 文档问答 | 文档 ID + 段落序号 |
| 客服 Agent | 应触发的工单类型 + 应调用的 API 名 |
| 数据分析 Agent | 应查询的表名与字段 + 结果数值区间 |
| 代码库问答 | 文件路径 + 符号名 + 起始行 |

判据是两条：**换个人标，标出来的东西一样吗？换个索引版本，它还能解析到吗？**

## 第三章：baseline 阶梯——把"好"拆成可归因的差分

有了题集，下一个问题最容易被答错："跟谁比"。

最容易想到的是跟 Claude Code、Cursor 这类成熟产品比。我没这么做，原因很实际：它们的模型版本、上下文长度、私有检索和工具权限我都统一不了，比出来的结果没法归因——赢了不知道赢在哪，输了也不知道输在哪。那是产品赛马。

我做的是**控制变量后的参考系统阶梯**：

| 臂 | 检索与回答路径 | 作用 |
|---|---|---|
| B0 | 外部 GitHub Code Search + 模板答案 | 外部关键词检索的下限参照 |
| B1 | 应用层 Okapi BM25 + 模板答案 | 稀疏检索参照 |
| B2 | dense-only 检索 + 共享的 Agent 合成与引用守卫 | **普通向量 RAG，主要对手** |
| B3 | BM25 + dense + 加权 RRF + rerank，再走同一套合成，但不开工具 | **强检索 baseline，最难打的对手** |
| B3.5 | 与 B4 相同的 Agent 循环，保留读文件与看大纲，**关闭全部图工具** | 诊断臂，见第五章 |
| B4 | 混合检索 + 完整 Agent 循环 + 全部图工具 | 完整系统 |

**这张表真正起作用的是下面这句：B2、B3、B3.5、B4 共用同一个合成模型、同一套 prompt、同一份引用协议、同一个 groundedness 守卫、同一个 14 步预算。**

差异只集中在检索模式和可用工具集合。只有这样，差分才有解释力：

- `B4 − B3`：完整 Agent 系统相对"一次检索 + 合成"的整体增益
- `B4 − B3.5`：Agent 保持不变、只拿掉图工具，才是**调用图的孤立贡献**
- `B3.5 − B3`：没有图的时候，Agent 多步读文件、挑证据的贡献

搭阶梯时我犯过一个错，值得单独提：早期版本里，只有 B4 按"答案中通过验证的最终引用"计分，B2、B3 按"检索返回的 top-k 候选"计分。**两边算的根本不是一个东西，B4 赢得毫无意义。** 后来统一成 v2 协议——四个 Agent 臂全部按已验证最终证据计分，同时把原始候选分也落盘备查。

顺带一个容易说错的口径：B4 的整体 `Recall@5 = 0.638` 是**最终引用证据**的 recall，而它初始混合检索候选的 recall 是 `0.560`。这两个数不能都叫"召回率"。

### 环境也要冻结

正式跑之前锁死的清单：

```
语料      psf/requests @ 414f0513…（37 文件 / 726 chunk / 473 边）
题集      questions.jsonl，SHA256 写进 provenance
embedding jinaai/jina-embeddings-v2-base-code（768 维）
reranker  BAAI/bge-reranker-v2-m3
合成模型  gpt-4o-mini，temperature 0.1
检索      BM25 与 dense 各取 50 → 加权 RRF（K=60，dense:sparse=2:1）→ rerank 前 16 → 取 5
预算      14 步硬上限，失败调用也计步
判据      composite 差 ≥ 0.05（见第四章）
```

题集 SHA 一定要记。不然跑完发现结果不好，随手改两道题再跑一遍，这事儿在自己一个人做项目的时候太容易发生了，而且发生了你自己都不一定记得。

还有两个容易漏的：

1. **改了代码要重新构建镜像。** Agent 跑在容器里，`restart` 会继续用旧代码。我有一轮就是这么废掉的。
2. **正式跑之前清一次工具结果缓存。** 我的工具缓存 24 小时，跑正式实验前执行一次 `FLUSHALL`。中途发现 Redis 命中了旧代码生成的图工具缓存，那一轮当场作废重跑——**中止的运行不算一轮有效重复**。

## 第四章：预注册判据——跑之前先写死什么算通过

这一章是整篇里最便宜、也最容易被跳过的一步。

跑完实验再决定"什么算成功"，你一定会（哪怕无意地）挑一个对自己有利的说法。数据在手上的时候，人的自我说服能力强得可怕。

所以在正式运行之前，我把成功标准写成了一条**可执行的规则**：

```
H1 supported
= L2 层：(B4 − B2) ≥ 0.05  且  (B4 − B3) ≥ 0.05
  且
  L3 层：(B4 − B2) ≥ 0.05  且  (B4 − B3) ≥ 0.05
```

两层 × 两个对手 = **四项比较，任意一项不满足，整体判 `unsupported`**。

其中：

- `composite` = `Recall@5`、`MRR`、`nDCG@5` 三者的均值
- `groundedness` 单独报告，**不进 composite**
- 只看 L2 和 L3。L1 是单文件事实题，一次检索就能解决，用它来证明 Agent 有用属于送分
- **0.05 是预先选定的工程门槛，不是统计显著性阈值**，我不会把它说成置信区间

关于 groundedness 不进 composite，这里有一段必须交代的账。最初 composite 是四项均值，包含 groundedness。但所有臂的 groundedness 恒为 1.000，把一个常数放进均值，等于把真实差异压缩到原来的 3/4。改成三项，等价于**把所有 margin 放大了 4/3**。

**这是一次对我自己有利的降标准。** 所以两种口径的结果我都保留了——好在最终两种算法下结论都是 `unsupported`，否则这一改就说不清了。

**如果你只从这一章拿一个动作走，就是这个：在跑正式实验之前，把成功判据写进代码或写进 README，并且 commit。** 成本五分钟，它买到的是你后面所有结论的可信度。

## 第五章：消融臂——B4 减 B3 其实混了两件事

我原本以为有了 B2、B3、B4 就够了。

问题是：B4 相对 B3 多了两样东西——**Agent 的多步取证循环**和**静态调用图工具**。`B4 − B3` 把这两件事混在一起。而我在调用图上花的时间最多，我当然很想说是它起了作用。

所以我加了 **B3.5**：完整保留 Agent 循环和读文件能力，**只关闭图相关的工具**。

结果是这样：

| 层级 | 调用图的贡献 `B4 − B3.5` | 多步取证的贡献 `B3.5 − B3` |
|---|---:|---:|
| L2 | +0.0218 | +0.0221 |
| L3 | +0.0226 | **+0.1466** |

**L3 上，多步取证的贡献约是调用图的 6.5 倍。**

这个结果对我个人来说不好受——花最多力气的模块，孤立贡献只有 0.023。但它是这次评测里信息量最大的一个数字：它说明这个系统的真正优势在于 Agent 会继续读代码并挑证据，调用图本身的孤立贡献很有限。

还有个数据点值得一提：11 个工具里的 6 个图工具，**有 4 个在整轮评测里从未产出过任何被引用的证据**。工具数量不等于工具贡献。

### 第二个例子：查询改写值多少

上面那个消融是在原项目上做的，你没法跑。配套的[共创项目](../Co-creation-projects/Odiethebest-CodebaseOnboardingAgent/)里有一个可以跑的，结论同样反直觉，值得单独讲。

「BM25 加向量之外要不要做查询改写」是个常见问题。多数做法是把改写加进检索链，然后在简历或文档里写一句"支持查询改写"。**更有用的做法是把它做成一个臂，测出它值多少。**

那边的改写是确定性的两步：按代码命名习惯做同义扩展（`strip` → `remove / clear / rebuild`），再用符号表回填（问题词与真实符号名有两个及以上重合时，把符号名补进查询）。然后拆成两个诊断臂：

- **B3Q**：改写后的查询同时给稀疏臂和稠密臂
- **B3Qs**：只给稀疏臂，稠密臂仍用原问题

10 道题上的结果：

| 臂 | 整体 composite | L2 相对 B3 |
|---|---:|---:|
| B3 混合检索 | 0.686 | —— |
| B3Q 改写两路 | 0.667 | +0.006 |
| B3Qs 只改稀疏 | **0.700** | **+0.066** |
| B4Qs 改写 + 多步取证 | 0.657 | +0.006 |

**朴素的改写是负收益。** 最能说明问题的是那道「basic auth 怎么挂到 prepared request 上」：改写扩展出的词里**正好包含 gold 符号 `_basic_auth_str`**，可这一题的分数从 0.790 掉到 0.472。**加对了关键词，结果反而更差。**

只改稀疏臂时，同一题稳在 0.790。原因在机制上：查询扩展本质是**词面**技术。BM25 拿到更多关键词会受益；稠密臂拿到的却是一串堆砌关键词的句子，句向量偏离了原始意图。

「把改写后的查询喂给整条检索链」是几乎所有人的默认写法，而它是错的。**不做这个消融，你不会知道；做了之后，同样的实现从 −0.019 变成 +0.014。**

第三行也值得看：改写和多步取证**不叠加**。两个各自有益（或至少无害）的增强放在一起，整体反而掉到 0.657，L3 上是 −0.105。它们抢的是同一批 top-5 名额。

### 一个必须守住的纪律

B3.5 给出的解释比 H1 本身有价值得多。所以会有一个很强的诱惑：**既然 `B4 − B3.5` 的故事更好听，那就把成功标准改成用 B3.5 当对手。**

不行。B3.5 是后加的诊断臂，代码里明确把它排除在 H1 判据之外。**消融可以改变我对系统的理解，不能改变已经锁定的判定。**

如果允许事后换对手，第四章那五分钟就白花了。

## 第六章：跑三轮才发现，轮间方差比判定门槛还大

跑一轮就下结论，是这套流程里最后一个、也是最贵的坑。

我跑了三轮。每轮 5 个内部臂 × 33 道题 = 165 次 arm-question 执行，三轮共 **495 次**。先看三轮均值的整体阶梯：

| 臂 | Recall@5 | MRR | nDCG@5 | Groundedness |
|---|---:|---:|---:|---:|
| B1 BM25 | 0.390 | 0.563 | 0.376 | 1.000 |
| B2 Dense RAG | 0.489 | 0.702 | 0.524 | 1.000 |
| B3 Hybrid + rerank | 0.553 | 0.795 | 0.587 | 1.000 |
| B4 完整系统 | **0.638** | **0.882** | **0.664** | 1.000 |

看起来很漂亮，阶梯单调上升。但 H1 判的是分层 composite：

| 层级 | B2 | B3 | B4 | B4−B2 | B4−B3 | 该层是否通过 |
|---|---:|---:|---:|---:|---:|---|
| L2（16 题） | 0.579 | 0.671 | 0.715 | +0.136 | **+0.0439** | **否**，差 0.0061 |
| L3（12 题） | 0.384 | 0.462 | 0.632 | +0.247 | +0.169 | 是 |

**四项通过三项，主假设 `unsupported`。**

到这一步为止，一个很自然的反应是："才差 0.0061，再调一调就过了。"

第三轮把这个念头打死了。看决定结论的那个 `L2 B4−B3` 在三轮里分别是多少：

| 重复 | L2 margin vs B3 | 单轮 verdict |
|---|---:|---|
| 1 | +0.0376 | `unsupported` |
| 2 | +0.0057 | `unsupported` |
| 3 | +0.0884 | **`supported`** |

**三轮极差约 0.083，比 0.05 的判定门槛本身还大。** 如果我只跑一轮，而那一轮恰好是第三轮，我会心安理得地写下"假设成立"。

检索是确定的，随机性来自合成模型最终挑哪几条引用（temperature 0.1 不是 0）。B1 三轮指标完全一致，正好当了个 sanity check——说明波动确实来自合成环节，不是 harness 有 bug。

所以 0.0061 的短缺**不是"再调一点就能过"**，因为它远小于运行间噪声。更诚实的下一步是扩题和加第二个仓库。

聚合方式也有个坑：**先逐题求三轮均值，再按层级聚合。** 不能把 495 行直接混在一起当独立样本——同一道题的三次重复不是三个独立观测。同时我保留了三轮各自的 verdict，防止均值掩盖翻转。

> **如果预算只够做一件事，跑重复比扩题更优先。** 你不知道自己的方差有多大，就不知道任何一个数字意味着什么。

## 第七章：你的指标能被系统反向刷高

这一章讲三个具体的、都在我项目里真实发生过的漏洞。它们的共同点是：**系统能在不变好的前提下让分数变好。**

### 漏洞一：删掉错误引用能提高正确率

系统里有个引用守卫：模型给出引用后，逐条去索引里核验文件、符号、行号，验不过的直接从正文删掉。

听起来很正确。但如果**按删除之后的引用集合计分**，系统就找到了一条捷径：先大量生成引用，反正错的会被删掉，留下的正确率自然高。

修法：**计分用删除前的引用集合。** 守卫保护用户，不保护指标。

### 漏洞二：不回答就能拿满分

groundedness 衡量"答案里的每句话是不是都有证据支撑"。旧逻辑里，一个**零引用的答案** groundedness 是 1.000——毕竟它没有任何无据的断言。

于是"什么都不说"成了最优策略。

修法：**零引用答案直接记 0 分。**

这两个洞还会互相遮蔽。我在修一个符号匹配缺陷时做了三个臂的对照实验：

| 臂 | 做法 |
|---|---|
| original | 保留符号 token，守卫做精确匹配 |
| A | 不再把符号 token 给模型，守卫仍精确匹配 |
| B | 保留 token，守卫先精确匹配，再补一次 dotted suffix 匹配 |

每臂跑三次，共九次单臂运行。**A 一开始看起来最好**——直到发现它让模型在部分问题上干脆没有可引用的内容，而旧的零引用记 1.0 规则**奖励了这个行为**。把零引用改成 0 分之后，A 的优势立刻反转，B 才是真正的赢家。

修好之后，每轮通过验证的引用数从 original 的 54 / 48 / 51 上升到 B 的 65 / 62 / 67。

> 注意这个结果的边界：九次都只跑 B4，用的是更早的 16 题集，没有完整 baseline 对照。**它证明了共享匹配规则让更多真实引用存活，不能拿来证明 H1 改善。** 不同配置的快照不能纵向拼成涨幅。

### 漏洞三：改动同时提高指标又让你受益

早期检索候选里，**测试目录占了 47%**。我加了一条过滤把测试文件排除，候选里的测试代码降到 0%。

而我的标准答案里本来就没有测试文件。**所以这个改动会机械地提高所有指标。**

它是不是该做？是，从产品角度测试代码确实不该当作实现依据。但它同时也是一次对我有利的口径调整，**这个利益冲突必须写进报告里主动声明**，不能当成系统变强了。

这类改动的判断标准是：**如果它让指标变好的方式绕过了你想测的能力，那就是刷分。** 至少要在报告里单列它的影响。

### 漏洞四：在测试集上选超参

这条最隐蔽，因为它看起来像正常调优。

共创项目里那个查询改写有一个 `max_expand` 参数（最多扩几个词）。在同一批 10 道题上扫一遍：4 → 0.703，8 → **0.731**，12 → 0.700，20 → 0.704。

看起来该把默认值改成 8，还能写一句"经调优后提升 0.03"。

**但这个扫描是在测试集上做的。** 选出 8 的那一刻，测试集就变成了开发集，0.731 这个数已经不再是对未见数据的估计。要定这个参数，得有一个独立的开发集，或者做交叉验证。

所以那边保留了最初选的 12，把敏感性表原样报出来。**报告一个更差的默认值加一张敏感性表，比报告一个调优后的最优值更诚实，也更有信息量**——读者能自己看出这个参数有多敏感。

顺带一个基础设施上的坑，同样来自那个改写函数：原本写的是 `for t in set(...)`。**Python 的 set 迭代顺序随 `PYTHONHASHSEED` 变**，截断到 `max_expand` 时选中的词每次运行都不同，那张敏感性表连跑两次能差 0.02。评测代码里凡是"取前 N 个"，前面那个集合必须是有序的——否则你以为的确定性根本不存在。

## 第八章：结论是 unsupported，然后呢

现在回到开头那句：主假设 `unsupported`，四项过三项，差 0.0061。

这个判定来自 harness 跑完自己落盘的 `h1_report.json`，有产物可查。结构大致是这样（数值为实际结果，字段名按记忆整理）：

```json
{
  "verdict": "unsupported",
  "passed": "3/4",
  "per_stratum": {
    "L2": {"n": 16, "B4_minus_B2": 0.136, "B4_minus_B3": 0.0439},
    "L3": {"n": 12, "B4_minus_B2": 0.247, "B4_minus_B3": 0.169}
  },
  "per_repeat_verdict": ["unsupported", "unsupported", "supported"]
}
```

最后那行是我特意让它单独输出的：**三轮里有一轮是 supported。** 只报均值的话，这件事就消失了——而它恰恰是第六章那个结论的来源。

我保留了它。也保留了早期失败的运行、废弃的评分协议、以及那些配置不同、不能与最终结果合并的历史快照：

| 阶段 | 发生了什么 | 怎么用 |
|---|---|---|
| smoke | 单臂临时题跑通 harness | 不计成绩 |
| suite | stub embedding + identity rerank，dense 召回为空，三个臂退化成同一条路径 | 证明 harness 能跑，也暴露环境不具备评测条件 |
| real | 第一次接真实 embedding、reranker 和合成模型 | baseline 首次拉开 |
| v1 协议 | 各臂计分规则不对称 | 已废弃 |
| v2 统一 | 四个 Agent 臂统一按已验证最终证据计分，首次加入 B3.5 | 单次快照，不能代替重复 |
| repeat3 | 相同配置正式跑三轮并逐题平均 | **当前唯一 H1 结论** |

为什么不把它调过去？

技术上我完全做得到：把成功标准换成 `B4 − B3.5`，或者恢复四项 composite，或者只报第三轮，或者在 L2 里补几道更吃多步取证的题。**每一条单独看都能找到理由。**

但只要做了其中任何一条，这套评测就不再是评测了，它变成了一个说服工具。而我最初搭它，是想知道答案。

保留 `unsupported` 换来了三样东西：

1. **它给了我一个真实的下一步。** 因为知道波动大于效应，我知道该扩题集和加第二个仓库。
2. **它让 B3.5 那个发现变得可信。** 如果我连自己的主假设都愿意调，那"多步取证贡献是调用图 6.5 倍"这个结论凭什么信？
3. **它经得起追问。** 一个说"我的系统全面优于 baseline"的报告，只要被问一句"L2 上对最强 baseline 领先多少"，就会碎。

顺带说一个更实际的：在答辩、面试或者代码评审里，**"我们预注册了判据，最后没通过，差 0.0061，而且三轮方差比门槛还大"** 这句话的说服力，远高于任何一个漂亮的百分比。前者证明你懂评测，后者只证明你会跑脚本。

### 我这次评测的已知缺口

同样列出来，因为一份不写缺口的评测报告不值得信：

- 单一 Python 仓库、33 道题（L2 16 / L3 12），单题权重大，不能外推到其他语言和大型仓库
- 没有和通用 Coding Agent 做统一条件下的端到端对比
- 没有真实用户 A/B——"帮助新人 onboarding" 目前仍然只是应用假设
- 没有人工双人标注，也没做自动指标与人工评分的相关性验证
- Judge 仍是 stub，`pairwise_win_rate` 没测；所以这套评测只回答一个问题："有没有找到并引用正确代码"
- `graph_reverse` 的 17 道题来自系统自己的图，可能漏掉图本身看不到的链路
- 三轮揭示了方差，但样本量不足以稳定估计小于 0.05 的效应

## 第九章：把这套接到 HelloAgents 上

前面八章都是方法。这一章说怎么把它变成读者能直接用的东西——**让它长得像框架自带的**。

第十二章的评估模块目录是这样组织的：

```
hello_agents/
└── evaluation/
    └── benchmarks/
        ├── bfcl/            # dataset.py / evaluator.py / metrics.py / ast_matcher.py
        ├── gaia/            # dataset.py / evaluator.py / metrics.py / quasi_exact_match.py
        └── data_generation/ # dataset.py / llm_judge.py / win_rate.py
```

自建评测完全可以沿用同一套约定，加一个 `custom/`：

```
hello_agents/
└── evaluation/
    └── benchmarks/
        └── custom/
            ├── dataset.py     # 锚点式题集加载与校验
            ├── evaluator.py   # 阶梯对照 + 预注册判据 + 重复运行
            └── metrics.py     # Recall@k / MRR / nDCG@k
```

保持和 `BFCLEvaluator` 一致的调用契约（`dataset → evaluator → evaluate → export_results`），学过第十二章的人不用重新学：

```python
from hello_agents import SimpleAgent, HelloAgentsLLM
from hello_agents.evaluation import AnchorDataset, LadderEvaluator

# 1. 加载锚点式题集（每题带 taxonomy 与 1~N 个 gold 锚点）
dataset = AnchorDataset(path="./questions.jsonl")
dataset.load()
dataset.freeze()          # 记录 SHA256，跑完可核对题集没被动过

# 2. 声明对照阶梯：键是臂名，值是"怎么回答一道题"
#    共享同一个合成模型与 prompt，差异只在检索与工具
ladder = {
    "B2": dense_only_arm,
    "B3": hybrid_rerank_arm,
    "B4": full_agent_arm,
}

# 3. 预注册判据——注意这一步在 evaluate 之前
evaluator = LadderEvaluator(
    dataset=dataset,
    arms=ladder,
    metrics=["recall@5", "mrr", "ndcg@5"],
    decision_rule={
        "treatment": "B4",
        "controls": ["B2", "B3"],
        "strata": ["L2", "L3"],
        "min_margin": 0.05,      # 每项都要过
        "aggregate": "mean",     # composite = 三项均值
    },
    repeats=3,                   # 重复次数，用来暴露方差
)

# 4. 跑。逐题先对 repeats 求均值，再按 strata 聚合
report = evaluator.evaluate()

print(report["verdict"])          # "supported" / "unsupported"
print(report["per_stratum"])      # 每层每个对手的 margin
print(report["per_repeat_verdict"])  # 每轮各自的结论，防止均值掩盖翻转

evaluator.export_results(report, output_file="./results/h1_report.json")
```

设计上有几点是从踩坑里来的，值得照抄：

1. **`decision_rule` 是构造参数，不是 `evaluate()` 的参数。** 判据必须在跑之前确定，API 形状应该让"跑完再改判据"变得别扭。
2. **`repeats` 默认不该是 1。** 单轮结果没有方差信息。
3. **`per_repeat_verdict` 必须单独返回。** 均值是 `unsupported`、但某一轮是 `supported`，这件事本身就是结论的一部分。
4. **`freeze()` 记录题集 SHA。** 跑完对一次，确保题集中途没被动过。
5. **诊断臂（比如 B3.5）放在 `arms` 里可以跑，但不能出现在 `decision_rule.controls` 里。** 用类型约束把第五章那个诱惑挡在门外。

`metrics.py` 那三个指标都不复杂，核心是 gold 匹配的口径：

```python
def recall_at_k(retrieved, gold, k=5):
    """retrieved / gold 都是稳定锚点，不是 chunk UUID。
    锚点相等的判据要写死：文件路径 + 符号名 + 起始行是否落在同一 chunk 内。"""
    hit = sum(1 for g in gold if any(match(r, g) for r in retrieved[:k]))
    return hit / len(gold) if gold else 0.0
```

`match()` 这个函数看着不起眼，它其实是第七章漏洞的高发地——**匹配放松一点，所有指标一起变好。** 所以它应该是独立文件、独立单测、独立 review，不要藏在评估器里随手改。

## 第十章：一页速查与适用边界

### 自建评测的十步

| 步 | 动作 | 常见错误 |
|---|---|---|
| 1 | 冻结语料版本 | 边跑边改索引 |
| 2 | 定义"一道题"：问题 + 层级 + 来源 + 稳定锚点 | 用一段标准答案文字，改用 Judge 判 |
| 3 | 记录题集 SHA | 结果不好就随手改题 |
| 4 | 搭 baseline 阶梯，共享合成模型与 prompt | 各臂计分规则不一致 |
| 5 | **写死预注册判据并 commit** | 跑完再决定什么算通过 |
| 6 | 加消融臂隔离你最想邀功的那个模块 | 用 `完整 − 最强对手` 冒充单模块贡献 |
| 7 | 至少跑三轮 | 单轮就下结论 |
| 8 | 逐题求均值再按层聚合 | 把所有行当独立样本 |
| 9 | 过一遍反向刷分自查清单 | 计分用了后处理之后的结果 |
| 10 | 报告里写清缺口与利益冲突 | 只报好看的那个口径 |

### 这套方法适合谁

适合：垂直场景、有明确正确答案坐标、需要回答"某个模块值不值得做"的项目。

不适合：开放式生成（写作、对话陪伴、创意），那类还是得靠 LLM Judge + 人工，参考第十二章 12.4。

以及一句限定：**本章所有数字都来自一个三人课程项目，单个 Python 仓库、33 道题。方法可以借鉴，数字不能外推。**

- 共创项目 [Odiethebest-CodebaseOnboardingAgent](../Co-creation-projects/Odiethebest-CodebaseOnboardingAgent/)：本章方法的可跑实现，含六臂对照与预注册判据
- 第十二章 12.1–12.4：公开基准与 LLM Judge 的标准做法，本章是它在垂直场景下的补充
